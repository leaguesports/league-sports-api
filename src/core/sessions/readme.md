A session is a single round / game.

`POST /api/sessions` starts a live session from `{ sport, config, venueId?, name?, sportData?, invited? }`. The sport plug-in validates `config` and builds the starting state. The server then opens one lobby with a join code and seats the creator (`role: creator`, `status: joined`) with a one-time participant token. `createdBy` is set from the signed-in user when the session cookie is present, and left empty otherwise.

`GET /api/sessions/join/:code` is public and rate-limited. It returns the sport, status, open spots, and participants as `{ id, name, status, role }` only. `POST /api/sessions/:id/join` claims an invite (`{ claimPid }`) or adds a player (`{ name, sportData }`). `POST /api/sessions/:id/leave` uses the `X-Session-Token` header. Core participant events are `participant.invited`, `participant.claimed`, `participant.joined`, and `participant.left`, written with the next `seq`.

`POST /api/sessions/:id/events` captures a sport event: `{ "type", "data", "clientEventId"? }` with the same `X-Session-Token` header. A missing or unknown token is 401. A token whose seat is not `joined` is 403, even if the session is already closed. A joined seat on a closed session is 409. `participant.*` stays on the join and leave routes, so posting one here is 400. Any other type must be in the plug-in's `acceptedEventTypes` and pass `validateEvent` (400 `{ error, details }`). The event is written with the next `seq` in the same transaction as `applyEvent` and the session state update. The row's `participantId` is the writer's seat and `createdBy` is their user id when they have one.

Golf accepts `hole.scored` (`{ participantId, hole, strokes }` with strokes 1–15) and `hole.cleared` (`{ participantId, hole }`). The target `participantId` must be a joined seat in this session. Any joined player may score for any joined player. State keeps the latest score per participant and hole, plus `scoredBy` (the writer) and `seq`. A hole is valid when it sits on the round: 1–18 by default, 1–9 for `holesPlayed: "front9"`, 10–18 for `"back9"`. A `holes` snapshot (`{ n, par, si }`) must be exactly that set. `handicapAllowance` defaults to 1. Tee `par`, `rating`, and `slope` are optional and must be sent together; without them, or without a handicap index, the player is gross only. `players` and `standings` are derived on each event. Standings rank by stableford (higher first); a tie shares the position and is not split. The maths is in `src/sports/golf/scoring.ts`. An optional `clientEventId` dedupes an offline retry from the same seat: the same payload returns 200 `{ seq, state }` and writes nothing; a different payload for that id is 409. A new event returns 201 `{ seq, state }`. The `state` on a replay is the current card, not a snapshot from the original seq. Two in-flight requests with a new id can both insert; the id is for retry-after-timeout, not a unique constraint.

Padel's lineup cap is a placeholder of 2–4 until that sport picks a fixed format. Golf is 1–4, and a golf player needs a `teeId` from the setup's `tees` list. `handicapIndex`, when sent, is from -10 to 54.

`RecordSession` stores a finished session with no lobby and status `closed`. It uses the same plug-in to validate setup, build state, and fold events. Event `seq` is assigned by the server, starting at 1.

`POST /api/sessions/:id/finish` is the creator's joined seat only (`X-Session-Token`). Anyone else is 403, including a creator who has left. A session that is already closed is 409. It writes `round.finished` at the next `seq`, sets `status` to `closed` and `endedAt`, freezes golf standings onto `state.result`, and deletes the lobby. That is the same lobby delete as `closeSession`, inside the one transaction. Posting `round.finished` to the capture route is 400. Response `200`:

```json
{ "seq": 4, "status": "closed", "endedAt": "2026-10-19T12:00:00.000Z", "state": {}, "session": {} }
```

`GET /api/sessions/:id` is public, like the join summary: knowing the id (which that summary already returns) is enough. It does not require a token. The body is `{ session, state, participants }`. `session` omits `createdBy`. Participants are `{ id, name, role, status, sportData, joinedAt, leftAt }` — the join summary's fields plus the tee data the card needs. `userId`, `token`, and `tokenHash` are never included.

`SessionRepository.closeSession` sets status to `closed` and deletes the linked lobby. The foreign key is `Session.lobbyId`, so deleting the lobby clears it. `endedAt` is set by finish, not by `closeSession`.

After each committed live event the server publishes `{ seq, type, state }` on the Ably channel `session:{id}`. The message name is the event type. That covers `participant.invited`, `participant.joined`, `participant.claimed`, `participant.left`, captured sport events, and `round.finished`. A start that writes several events publishes each one with the state from the end of that transaction. A `clientEventId` replay publishes nothing. `RecordSession` is a historical log and does not publish. Publish runs after the transaction commits, from the `SessionEventCommitted` listener registered at startup. If `ABLY_API_KEY` is unset the process logs that once and skips. A publish failure is logged and does not change the HTTP response. The published body is the same state the route returns; it has no tokens.

Sport rules live in `src/sports/<sport>/session.ts` and are registered by id (`golf`, `padel`). Start, join, leave, capture, and record call the registry and do not branch on sport. `recordSession` folds events without a seat list, so a recorded golf round keeps scores and does not rebuild handicaps.
