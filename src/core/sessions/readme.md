A session is a single round / game. Sport rules do not live here. Each sport is a plug-in under `src/sports/<sport>`: it validates setup, decides who may sit down, and folds an event into the next state. Start, join, leave, capture, finish, and record call the registry and do not branch on sport.

`POST /api/sessions` starts a live session from `{ sport, config, venueId?, name?, sportData?, invited? }`. The sport plug-in validates `config` and builds the starting state. The server then opens one lobby with an 8-character join code and seats the creator (`role: creator`, `status: joined`) with a participant token. `createdBy` is set from the signed-in user when the session cookie is present, and left empty otherwise. Invites are `{ name, sportData? }`. The client cannot set an account id on an invite. `config` is limited to 4000 characters. The invite list is limited to 16 names. Start is rate-limited per address. The plug-in's `participants.max` is the seat cap.

`GET /api/sessions/join/:code` is public and rate-limited. It returns the sport, status, open spots, the public setup, and participants as `{ id, name, status, role }`. Public setup is the plug-in's `publicSetup`. `POST /api/sessions/:id/join` must send the same join code. It claims an invite (`{ claimPid, joinCode }`) or adds a player (`{ name, sportData?, joinCode }`). A player who has left can take that same name again. The seat keeps its id and gets a new token. `POST /api/sessions/:id/leave` uses the `X-Session-Token` header. `POST /api/sessions/:id/token` gives a signed-in player a new token for their joined seat. Core participant events are `participant.invited`, `participant.claimed`, `participant.joined`, and `participant.left`, written with the next `seq`. Plug-ins do not list these types. They still receive them, with the current seats, so a card can change when someone sits down or leaves.

`POST /api/sessions/:id/events` captures a sport event: `{ "type", "data", "clientEventId"? }` with the same `X-Session-Token` header. A missing or unknown token is 401. A token whose seat is not `joined` is 403, even if the session is already closed. A joined seat on a closed session is 409. `participant.*` and `round.finished` stay off this route, so posting one here is 400. Any other type must be in the plug-in's `acceptedEventTypes` and pass `validateEvent` (400 `{ error, details }`). `validateEvent` receives the seats and the writer's seat id. The event is written with the next `seq` in the same transaction as `applyEvent` and the session state update. The row's `participantId` is the writer's seat and `createdBy` is their user id when they have one.

`data` on the row is the client payload. The writer and `seq` are not copied into it. `applyEvent` receives them on the envelope: `{ type, data, seq, participantId }`. An optional `clientEventId` is stored on the row, not in `data`, and is unique per `(sessionId, participantId)` when it is set. The same type and payload from that seat returns 200 `{ seq, state }` and writes nothing. A different payload for that id is 409. Comparison is the whole client payload. A new event returns 201 `{ seq, state }`. The `state` on a replay is the current card, not a snapshot from the original seq. Two in-flight requests that pass the read can still race; the unique index rejects the second insert, and that request retries the read so it becomes a replay or a 409.

`RecordSession` stores a finished session with no lobby and status `closed`. It uses the same plug-in. The fold always receives the seat list the caller supplied (empty when omitted), so a recorded round and a live round run one function. Event `seq` is assigned by the server, starting at 1. A golf score in a recorded log needs the writer on the event envelope (`participantId`). It does not create participant rows.

`POST /api/sessions/:id/finish` is the creator's joined seat only (`X-Session-Token`). Anyone else is 403, including a creator who has left. A session that is already closed is 409. It writes `round.finished` at the next `seq`, sets `status` to `closed` and `endedAt`, lets the plug-in freeze its result onto `state`, and deletes the lobby. That is the same lobby delete as `closeSession`, inside the one transaction. Response `200`:

```json
{ "seq": 4, "status": "closed", "endedAt": "2026-10-19T12:00:00.000Z", "state": {}, "session": {} }
```

`GET /api/sessions/:id` is public, like the join summary: knowing the id (which that summary already returns) is enough. It does not require a token. The body is `{ session, state, participants }`. `session` omits `createdBy`. Participants are `{ id, name, role, status, sportData, joinedAt, leftAt }` — the join summary's fields plus the sport data the card needs. `userId`, `token`, and `tokenHash` are never included.

Stored `state` is a cache of the last fold. The event log plus the seats are what a replay must be able to rebuild. A locked result on that state is the plug-in's snapshot at finish; later folds do not rewrite it.

`SessionRepository.closeSession` sets status to `closed` and deletes the linked lobby. The foreign key is `Session.lobbyId`, so deleting the lobby clears it. `endedAt` is set by finish, not by `closeSession`.

After each committed live event the server publishes `{ seq, type, state }` on the Ably channel `session:{id}`. The message name is the event type. That covers `participant.invited`, `participant.joined`, `participant.claimed`, `participant.left`, captured sport events, and `round.finished`. A start that writes several events publishes each one with the state from the end of that transaction. A `clientEventId` replay publishes nothing. `RecordSession` is a historical log and does not publish. Publish runs after the transaction commits, from the `SessionEventCommitted` listener registered at startup. If `ABLY_API_KEY` is unset the process logs that once and skips. A publish failure is logged and does not change the HTTP response. The published body is the same state the route returns; it has no tokens.

Rate limits for start, join, and join lookup are stored in `SessionRateHit` so every server shares one count. Reactions to a started session subscribe at `handleSessionStarted`. They do not become new commands in this module.
